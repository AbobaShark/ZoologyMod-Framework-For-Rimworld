# Daily animal growth

Growth uses the installed species-specific LifeStageDefs from AnimalStats.
Neither the game nor Checker creates extra per-day LifeStageDefs. The original
life-stage boundaries, species attacks, graphics, reproduction and feeding rules
are retained.

## Model

For biological age \(a\) between successive race stage ages \(a_0\) and
\(a_1\), define

\[
t = \mathrm{clamp}((a-a_0)/(a_1-a_0),0,1).
\]

The game samples once per biological day (60,000 biological age
ticks), independently of world time and age acceleration. The actual
runtime progress for **all** supported numeric stats and the sprite is
normalized between the first and last sampled biological days inside the
stage. This reaches the next stage's starting numerical endpoint on the
last day before the switch, not one sample afterward. For an interval
with only one sample, the usual age fraction is retained. A stage
quantity with endpoints \(x_0\) and \(x_1\) is evaluated as
\(x=x_0+(x_1-x_0)t\), using that common sampled progress. The source
numbers remain the calculated AnimalStats stage endpoints, not hardcoded
species overrides. This is linear interpolation of the *game stage
factors*, not a claim that real body mass grows linearly.

The pawn's original RimWorld BodySize and HealthScale getters remain the
authority for all other modifiers. Growth replaces only the current-stage
coefficient by multiplying the original result by \(x/x_0\).
StatDef factors, hunger-rate multiplier, market value and natural attacks have
their own corresponding adjustments. When a natural attack is used, the correct
CE/vanilla stage coefficient is interpolated by Tool and attack component
(damage, cooldown, sharp AP, blunt AP); the shared Tool or LifeStageDef is
never mutated. Adult pawns retain the original behavior.

Maximum nutrition is **not** a separate interpolation. RimWorld's
`Need_Food.MaxLevel` already derives from the live `Pawn.BodySize` and the
life-stage `foodMaxFactor`. The animal's BodySize grows every biological day;
therefore `foodMaxFactor` must stay at 1 for the generated animal stages.
Applying `BiologicalStageMass_kg / AdultMass_kg` as an additional
`foodMaxFactor` double-counts growth: a medium predimago Harpactotyrannus
at BodySize 2.99 previously had maximum nutrition around 0.15 because
the old factor was 0.05. The same formula produced huge multipliers for
large Royal megachicken stages. AnimalStats now supplies unity throughout
`LifeStageProfiles!J2:J1246`; Checker exports the supplied profile value
and the runtime installer applies it without additional safeguards or
compatibility adjustments. The developer inspection action prints the live
food maximum and the factor.

## Natural-attack geometry

For each species-specific stage, the absolute lengths of the four
attack-related anatomical dimensions from `Base stats!W:Z` are first
converted to that stage's dimensions:

\[
L_{stage} = L_{adult}\left(\frac{M_{stage}}{M_{adult}}\right)^{1/3}.
\]

`SERVICE_LifeStageCalculations!W:Z` provides the stage-specific
values to the attack damage and Combat Extended penetration formulas.
Downstream bite, claw, limb and specialized-attack calculations refer
to these cells rather than rereading adult lengths. The mass-dependent
physical models and adult source values are otherwise preserved.

Contact-width formulas in `CC` and `CM` retain their existing 0.05
quantization when it produces a positive result. Where that
quantization would turn a physically positive width into zero, they
carry the unrounded width into the later attack equations. This
prevents very small juvenile stingers or teeth from disappearing
because of premature numerical rounding; the final output is still
serialized by Checker at its existing precision.

Identical morphology *classes* do not imply identical absolute
lengths: at 50 kg Harpactotyrannus and Arthropython share the
Spectrobionta jaw-force model, but their calculated tooth lengths
are about 5.69 cm and 2 cm respectively. Their CE sharp penetration
therefore need not match or increase in the same order as game BodySize,
which is not a literal body-mass measurement.

Stage movement-speed factors are intentionally not generated by a
single adult-speed conversion for every animal. LifeStageProfiles retains
the earlier biologically motivated juvenile speed treatment, including
direct physical-speed scaling for crocodilians and selected theropods and
the minimum speed factors for specified small mammal young. These
exceptions affect only Vanilla and CE movement speed, not damage, armor,
metabolism, or other stage calculations.

For consecutive stages using the **same artwork**, the root transform keeps
the original BodySize-normalized interpolation of authored
`bodyGraphicData.drawSize`. No pixel measurement is required for that
transition.

For a **change of artwork**, the visible alpha bounding rectangle is
measured separately for North, East, South and West. Its width and height
are multiplied by the corresponding graphic's authored drawSize to
express visible dimensions in world units. The largest permitted scale
of the outgoing graphic is calculated once: the minimum of the ratios
between the next graphic's starting visible width/height and the
outgoing graphic's unscaled visible width/height across all facings.
One uniform scale is used in both dimensions, without distortion.

Crucially, this is the **last-day target**, not a clamp evaluated on
every day. The outgoing graphic interpolates from its starting scale
to that target over the entire interval. Progress for visual interpolation
is normalized to the first and last *actual biological-day samples*
before the transition, so the last day reaches the target rather than
stopping one fraction short. The limiting width or height may exactly
equal that of the next stage at the transition; the other dimensions
are no larger.

If the outgoing artwork is too large even at its original stage start,
the starting scale must also be reduced or the interval would require
the animal to shrink. The reduction is based on the ratio of the
installed starting and ending life-stage BodySize factors. Where this
also affects preceding stages using identical artwork, they retain
the same original growth curve multiplied by one shared factor,
avoiding an additional jump at their common graphic boundary.
For consecutive changes of artwork, the next stage's *actual adjusted
starting scale* is used rather than assuming it must always be 1.

The alpha bounding box uses pixels with alpha >= 12/255. CPU-readable
textures are measured directly; non-readable textures receive a one-time
256x256 GPU readback. Texture measurements and the stage endpoint plan
are cached per texture and kind/sex respectively. No texture processing
runs each biological day or each rendered frame. If a graphic cannot
be measured, its transition retains the original interpolated scale.
No artwork dimensions, biological parameters, life-stage definitions,
or textures are mutated.

The debug action **Zoology -> Inspect animal life-stage profile** prints
the absolute current/next sprite widths and heights, the calculated
starting scale, last-day target, visual progress and current interpolated
scale. These values can distinguish a bad texture measurement from a
rendering hook that failed to apply the calculated scale.

Spectrobionta are interpolated between consecutive life stages *within the
same race*: e.g. small -> medium -> large predimago when those stages exist
in that race's lifeStageAges. Metamorphosis between different races/PawnKindDefs
is not an interval in a single race's lifeStageAges and therefore remains
discrete. No stage is excluded solely because its name starts with
Spectrobionta. Unmapped animal defs and missing kind graphic data safely
retain vanilla behavior. Actual stage transitions remain discrete.

## Performance design

- One per-pawn snapshot is lazily recomputed once per biological day
  or after a change of current stage/kind. The visual size endpoint plan
  is calculated once per PawnKindDef/sex; daily visual interpolation uses
  only two cached scale endpoints and the current biological day.
- Snapshots use weak keys, with no world or map-wide pawn scan, polling
  component, persistent save data, LINQ, or per-tick allocation.
- Species stage intervals and stat-factor dictionaries are built once
  at startup, after species-specific stage installation.
- Harmony getters perform only indexed/dictionary lookups and a cached
  multiplicative factor during normal execution.
- Stat parts are installed only on stats whose stage factors differ and
  MarketValue; natural-attack factors are read only on demand.
- Full render-tree preparation, graphics loading and texture rebuilding
  are *not* performed by this system. Root scaling is restricted to actual
  young animals and preserves existing node transforms.

No numerical FPS/TPS guarantee is implied. Runtime comparison with the
growth patch disabled is required to quantify overhead and detect
interactions with external performance mods.

## Required in-game validation

1. Load RimWorld 1.6 and 1.7 with the generated stage profiles. Confirm the
   log contains daily growth initialization, and no Harmony patch errors.
2. Use **Zoology → Inspect animal life-stage profile** in developer mode.
   Select newborn, mid-stage and near-stage-boundary animals. The diagnostic
   reports biological stage progression, BodySize/HealthScale multipliers,
   visual root scale and actual stage/combat stats.
3. Compare BodySize, HealthScale, MoveSpeed, MarketValue, hunger-rate
   behavior, actual `Need_Food.MaxLevel` and sprite footprint before/after
   biological-day boundaries. Nutrition capacity should follow the live
   animal BodySize, including the day before a stage transition, without
   additional mass-fraction suppression or huge Royal megachicken factors.
   Values must remain unchanged within the same biological day, change on
   the following day, and match stage endpoints at transitions.
4. Specifically exercise tiny baby birds, swine, the Royal megachicken with
   five stages, a large theropod, crocodiles and a Spectrobionta animal.
   Test the first, middle and last biological days of each interval with
   a different texPath, as well as the first day of the next stage, in all
   four facings. Visible sprite dimensions should grow on each daily step
   and the last day must not exceed the subsequent sprite's starting
   visible width or height. Confirm there is no early plateau. Compare
   the diagnostic start/end scales and measured visible dimensions when
   behavior differs. Unchanged-texPath intervals must retain the original
   interpolation curve, up to any necessary shared group multiplier.
   For Spectrobionta, verify growth inside each race without interpolating
   metamorphosis into a different race/PawnKindDef.

5. With and without Combat Extended, compare actual natural attack damage,
   cooldown, both armor penetrations and CE armor durability at young and
   adult stages, and confirm there is no double scaling.
6. Test barn-contained animals as they grow. Existing 150-tick placement
   refresh must react to changed BodySize, avoid crossing fences, and stay
   within displayed occupancy limits.
7. Save/reload during a stage, age animals while unspawned, and confirm
   snapshot recovery without daily replay or additional save records.
8. Profile 1000 young animals for TPS and a zoomed-in mixed barn for FPS,
   comparing the same save with and without this runtime feature.

Source locations: `ZoologyAnimalGrowth.cs`,
`ZoologyAnimalGraphicBounds.cs`,
`ZoologyAnimalGrowthStatPart.cs`,
`Patch_ZoologyAnimalGrowth.cs`, and the existing
`ZoologyLifeStageProfileInstaller.cs`.

## Pedomorphosis compatibility

Spectrobionta pedomorphosis stops biological age inside the current race.
The daily growth snapshot depends on biological age day, stage and PawnKind,
so it naturally retains the same BodySize, HealthScale, movement, attack
coefficients and render scale as long as the age remains frozen. Releasing
pedomorphosis resumes biological growth on subsequent biological days.
No special per-pawn polling is required in Zoology and no stage transition
or metamorphosis is simulated by interpolation.

Keep `SpectrobiontaPredimagoMedium` as a distinct stage even though the
small and medium predimagos share the Carnophagus texture. It supplies a
biologically calculated piecewise growth endpoint and, independently, a
second allowed pedomorphosis stop, while the graphic transition to the
Harpactotyrannus appearance remains at `SpectrobiontaPredimago`.


## Debug age actions and compiled assemblies

`Make +1 Day Older` and `Make +1 Year Older` change the pawn's
biological age. The growth snapshot is keyed by the resulting biological
day, so the vanilla debug actions require no special hooks. Each year in
RimWorld contains 60 biological days: a one-year increment can cross
several stages in a single action and therefore cannot demonstrate the
visual interpolation inside those skipped intervals. For a valid check,
use repeated one-day increments on a young animal.

RimWorld executes `ZoologyMod.dll`, **not** C# files in `Source`.
Updating the Git checkout or regenerating `LifeStageProfiles_Generated.xml`
does not compile the DLL. After changing source code or generated attack C#,
rebuild the assembly for the actual RimWorld version and restart the game.
For RimWorld 1.7 the loaded file is
`Zoology/1.7/Assemblies/ZoologyMod.dll`. The repository's binary was
last updated on 2026-11-05, before dynamic growth source was introduced
on 2026-11-08. The 1.6 and common assemblies are older still.
Do not infer support from the presence of new `.cs` files.

Select a pawn using **Zoology -> Inspect animal life-stage profile** after
rebuilt assembly deployment. The result reports biological age ticks,
current biological day, Harmony hook presence, stage specialization,
interval progress, BodySize/HealthScale ratios and draw scale. If the
interval is unavailable, the reason is printed. Compare the diagnostic
before and after several `Make +1 Day Older` operations; both the
effective BodySize and draw scale should change while the same
life-stage index remains active. If body ratios change but graphics do
not, investigate rendering/cache behavior, not AnimalStats formulas.
If Harmony hooks show false, inspect the compiled DLL and runtime patch
settings. These developer-only checks add no per-tick overhead.
